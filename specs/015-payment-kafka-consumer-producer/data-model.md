# Data Model: payment-api como Consumidor e Produtor Kafka

## Entidade existente evoluída: `Payment` (tabela `payments`)

Colunas atuais (V1): `id UUID PK`, `order_id VARCHAR(255) NOT NULL`, `amount NUMERIC(19,2)
NOT NULL`, `status VARCHAR(20) NOT NULL`, `created_at`/`updated_at TIMESTAMPTZ NOT NULL`.

Mudanças (migração `V2__payment_event_support.sql`):

| Mudança | Detalhe |
|---|---|
| Nova coluna `source_event_id` | `UUID`, **nula**. Preenchida só em pagamentos decididos a partir de `OrderCreated` (o `eventId` de entrada). Nula nos criados por `POST /api/payments`. |
| Índice único `ux_payments_source_event_id` | em `(source_event_id)` — Postgres permite vários nulos; garante dedup por `eventId` (FR-004). |
| Índice único parcial `ux_payments_order_id_from_event` | em `(order_id) WHERE source_event_id IS NOT NULL` — no máximo um pagamento decidido por evento por pedido (FR-005); não afeta pagamentos REST. |

`PaymentStatus` ganha `FAILED` (além de `RESERVED`, `CONFIRMED`, `CANCELLED`). Transições:

```text
(evento OrderCreated, valor <= limite) → RESERVED → CONFIRMED | CANCELLED   (inalterado, via REST)
(evento OrderCreated, valor >  limite) → FAILED                              (terminal)
```

`confirm`/`cancel` de `FAILED` lançam o `InvalidStatusTransitionException` já existente (409).
`PaymentResponse` não muda; só passa a poder trazer `"FAILED"` em `status`.

## Nova entidade: `OutboxEvent` (tabela `outbox_events`)

Mesmo esquema do E2.2 (ver
[`specs/014-order-kafka-producer/data-model.md`](../014-order-kafka-producer/data-model.md)),
criado no `payment_db` na mesma migração `V2`. Existe só enquanto pendente; removido após o ack.

| Coluna | Tipo SQL | Nulo | Regra |
|---|---|---|---|
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | não | PK; ordem de entrega (pode ter lacunas) |
| `event_id` | `UUID` | não | **UNIQUE**; é o `eventId` do payload, estável entre reentregas |
| `event_type` | `VARCHAR(50)` | não | `PaymentReserved` \| `PaymentFailed` |
| `topic` | `VARCHAR(100)` | não | `payment.reserved` \| `payment.failed` |
| `aggregate_id` | `UUID` | não | `orderId`; **chave Kafka** |
| `payload` | `TEXT` | não | JSON já serializado (Jackson 3) |
| `trace_id` | `VARCHAR(64)` | sim | `traceId` do MDC no enqueue (origem) |
| `occurred_at` | `TIMESTAMPTZ` | não | instante da decisão (= `occurredAt` do payload) |
| `created_at` | `TIMESTAMPTZ` | não | instante da gravação no outbox |

> `aggregate_id` é `UUID` porque o `orderId` do `order-api` é um UUID e o contrato do E2.1 o
> define como "string no formato UUID". Uma mensagem de entrada com `orderId` que não seja UUID
> válido é tratada como **ilegível** (descartada com log, FR-011).

## Eventos — ver [contracts/payment-events.md](./contracts/payment-events.md)

| Classe | Direção | Envelope | Campos específicos |
|---|---|---|---|
| `OrderCreatedMessage` | entrada | `eventId`, `eventType`, `eventVersion`, `occurredAt`, `orderId` | `customerId` (String), `amount` (BigDecimal) |
| `PaymentReserved` | saída | sim | `paymentId` (UUID), `amount` (BigDecimal) |
| `PaymentFailed` | saída | sim | `reason` (String, ex.: `AMOUNT_LIMIT_EXCEEDED`) |

Regras de geração dos eventos de saída: `eventId = UUID.randomUUID()` no enqueue;
`eventVersion = 1`; `occurredAt` = instante da decisão (o `createdAt` do pagamento);
`orderId` = o do `OrderCreated` de origem (não o id do pagamento).

## Fluxo de processamento de um `OrderCreated` (uma transação)

```text
parse JSON ── inválido/campo obrigatório ausente ──→ log ERROR, retorna (offset avança)
   │
   ▼ (válido)
BEGIN
  existsBySourceEventId(eventId) ou existe pagamento-de-evento para orderId ──→ log "duplicate", COMMIT (nada a fazer)
  decisão = PaymentDecisionPolicy(amount)
  INSERT payments(... status = RESERVED|FAILED, source_event_id = eventId)
  INSERT outbox_events(PaymentReserved | PaymentFailed)
COMMIT  ──→ offset confirmado depois (ack-mode BATCH)
erro transitório (banco) ──→ exceção; DefaultErrorHandler repete a cada 1 s, sem descartar
violação de constraint (corrida) ──→ rollback; reentrega; pré-checagem acha duplicata
```

Parâmetro: `payment.approval.limit` (padrão `1000.00`); `amount > limit` ⇒ `FAILED`
(`compareTo`, então `1000` e `1000.00` são "dentro").
